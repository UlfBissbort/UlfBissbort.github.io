Exploring Go's Scheduling Through a Rust Implementation

One thing I like about Go is that I can write a goroutine that does a lot of computation without having to sprinkle yield calls throughout my code. Another goroutine can still get a chance to run. Even if I set GOMAXPROCS=1, so only one Go processor is available to execute Go code at a time.

I understood this at the level of "the runtime takes care of it." But that leaves a fairly substantial question unanswered. If the CPU is busy executing my loop, and my loop never calls the runtime, where does the code that stops it actually run?

Does another thread reach in and change something? Does the running thread interrupt itself? And once we have stopped it, where do we put the computation so we can continue it later?

I wanted to understand this more concretely. So I started building small experiments in Rust, using assembly where we need to get below what an ordinary Rust function can express. The experiments here run on macOS on ARM64. The exact registers and signal structures are platform-specific, but the questions are not.

There is one qualification to make before we start. Modern Go can asynchronously preempt ordinary Go code, including tight loops without function calls. This does not mean every goroutine can be stopped safely at every instruction, or that scheduling provides a hard latency guarantee. The distinction becomes important once we try doing this ourselves.

Where is a computation while it is running?

Let's say we have computation A running a loop, and we would like computation B to run for a while instead.

Rust
let mut total = 0u64;
for i in 0u64..500_000_000 {
    total = total.wrapping_add(std::hint::black_box(i));
}

The black_box is there to discourage the compiler from replacing our experiment with something much less interesting. We want an actual computation that occupies the CPU.

At some point during this loop, where is A?

Some of it is in memory. The executable instructions are in memory. Its stack is in memory. Any heap allocations it refers to are in memory. But some of its current state is in the CPU's registers: intermediate values, the stack pointer, the address of the next instruction, condition flags, and possibly floating-point or vector values.

If we start using those registers for B, we will overwrite A's values. So we need to put them somewhere first.

The natural place is another region of memory. We can write register values into a struct and later load them back. The stack does not have to be copied every time. We can leave A's stack allocated where it is and give B a different one.

This was the first part I wanted to make concrete: a suspended computation can be represented by saved register state together with memory that remains alive.

It is tempting to call this a serialized computation. In a limited sense it is. But it is not a portable blob we can write to disk and restore in an unrelated process. The saved state contains addresses into this process. It may refer to heap objects, operating-system resources, or thread-local data. Saving registers does not collect all of those dependencies for us.

We also do not save the CPU's caches or branch predictor. Those affect how quickly execution proceeds, but they are not private state that we have to restore to make A's instructions compute the same result. We are interested in the architecturally visible state needed to continue execution.

What would switching actually look like?

For the first experiment, let's make life easier. A agrees to call a function that switches away from it. We are not interrupting it at an arbitrary instruction yet.

This gives us something useful: a calling convention.

The compiler already knows that a function call may overwrite certain registers. If a value needs to survive the call, the compiler must arrange for it to survive. Other registers are callee-saved: the called function promises to preserve them.

On AArch64, our cooperative context switch saves the following state:

Rust
#[repr(C)]
#[derive(Debug, Clone)]
struct Context {
    x19: u64, x20: u64, x21: u64, x22: u64, x23: u64,
    x24: u64, x25: u64, x26: u64, x27: u64, x28: u64,
    x29: u64,   // frame pointer
    x30: u64,   // link register
    sp:  u64,   // stack pointer
    d8:  u64, d9:  u64, d10: u64, d11: u64,
    d12: u64, d13: u64, d14: u64, d15: u64,
}

The #[repr(C)] matters because our assembly uses fixed offsets into this structure. We need the layout to match those offsets.

The d8–d15 fields hold the ABI-preserved lower 64 bits of eight SIMD registers. They are easy to overlook if you are thinking only about integer registers. The compiler is not obliged to share that preference.

This is 168 bytes of saved context. It is not the entire state of an arbitrary interrupted computation. It is the context our switch needs at this particular kind of call boundary.

Here is the actual switching function. It is worth looking at the whole thing once, because there is no scheduler hidden inside it.

Rust
#[unsafe(naked)]
unsafe extern "C" fn switch_context(
    _old: *mut Context,
    _new: *const Context,
) {
    naked_asm!(
        "stp x19, x20, [x0, #0]",
        "stp x21, x22, [x0, #16]",
        "stp x23, x24, [x0, #32]",
        "stp x25, x26, [x0, #48]",
        "stp x27, x28, [x0, #64]",
        "stp x29, x30, [x0, #80]",
        "mov x2, sp",
        "str x2, [x0, #96]",
        "stp d8, d9, [x0, #104]",
        "stp d10, d11, [x0, #120]",
        "stp d12, d13, [x0, #136]",
        "stp d14, d15, [x0, #152]",

        "ldp x19, x20, [x1, #0]",
        "ldp x21, x22, [x1, #16]",
        "ldp x23, x24, [x1, #32]",
        "ldp x25, x26, [x1, #48]",
        "ldp x27, x28, [x1, #64]",
        "ldp x29, x30, [x1, #80]",
        "ldr x2, [x1, #96]",
        "mov sp, x2",
        "ldp d8, d9, [x1, #104]",
        "ldp d10, d11, [x1, #120]",
        "ldp d12, d13, [x1, #136]",
        "ldp d14, d15, [x1, #152]",
        "ret",
    );
}

The arguments arrive in x0 and x1. stp stores a pair of registers; ldp loads a pair. The first half writes the old state into memory. The second half loads the new state.

A naked function lets us provide this instruction sequence without the compiler adding an ordinary function prologue and epilogue around it. That would be rather inconvenient when we are replacing the stack those instructions would normally operate on.

So at which instruction do we stop being A and become B?

There is not one instruction that changes an abstract thread identity. We progressively replace the state. At mov sp, x2, we start using the new stack pointer. At ret, control transfers to the address we loaded into x30. By then, the registers in this context have been restored as well.

On AArch64, ret normally branches to x30, the link register. It does not check whether that address belongs to the function that called us. If x30 contains B's saved continuation, that is where we go.

From B's perspective, its earlier call to switch_context has just returned.

But what if B has never run before?

Then there is no saved continuation yet. We have to construct one.

This is the relevant setup from the experiment:

Rust
let stack = vec![0u8; STACK_SIZE];
let stack_top = stack.as_ptr() as u64 + STACK_SIZE as u64;
let stack_top = stack_top & !0xF;

let mut ctx = Context::zeroed();
ctx.sp = stack_top;
ctx.x30 = thread_wrapper as u64;
ctx.x19 = f as u64;
ctx.x29 = 0;

We allocate a stack, align its top to 16 bytes, and arrange for the first switch to enter thread_wrapper. The stack grows downward. The owned allocation has to remain alive for as long as this computation might resume.

The wrapper calls the function whose address we put in x19:

Rust
#[unsafe(naked)]
unsafe extern "C" fn thread_wrapper() {
    naked_asm!(
        "blr x19",
        "bl {done}",
        "brk #1",
        done = sym thread_done,
    );
}

When the user function returns, thread_done marks it finished and switches away. We cannot just let it return into an imaginary caller beyond the top of its stack.

There are deliberately missing pieces here. A heap allocation of a fixed size is not a growable stack, and this example does not install a guard page to catch overflow. It is enough to investigate the switch, not enough to make arbitrary functions safe to run on it.

Who is doing the switching?

At this point, no second OS thread is involved.

A calls the switching function. The switching function executes on the same OS thread, initially using A's stack. It saves A's context and restores another context. That context could belong directly to B, but it is convenient to return to a scheduler first.

The scheduler is ordinary code too. It runs on the OS thread's original stack and has its own saved context. Its job is to choose which ready computation to resume.

Conceptually, the loop looks like this:

Rust
// Sketch of the control flow, not a standalone Rust implementation.
loop {
    let Some(next) = pick_ready_thread() else { break };
    mark_running(next);
    unsafe {
        switch_context(scheduler_context, next.context);
    }
    // The selected thread has yielded or finished.
}

Yielding does the reverse: mark A ready, save A's context, and restore the scheduler's context.

An early version made the mistake of calling the scheduling loop from the yield function. But calling another Rust function does not move us to the scheduler's stack. It adds another call on the current stack. Repeating that is not the suspension mechanism we wanted.

The scheduler must be resumed, not recursively called.

This also answers part of the question about cores. We are switching computations on an OS thread. The operating system may move that thread between physical cores independently. Our little runtime does not need to select a core or change which address space the CPU is using.

But we have not answered the original question yet. A still has to call us.

What if A never yields?

One approach is to ask A to check occasionally whether it has run long enough.

The experiment uses a timer that delivers SIGALRM. The handler sets a flag:

Rust
static SHOULD_YIELD: AtomicBool = AtomicBool::new(false);

extern "C" fn alarm_handler(_sig: i32) {
    SHOULD_YIELD.store(true, Ordering::Relaxed);
}

fn check_preempt() {
    if SHOULD_YIELD.swap(false, Ordering::Relaxed) {
        yield_now();
    }
}

If the loop calls check_preempt(), the timer can influence when it yields. But if we remove those calls, the flag just sits there being true. Nothing about setting it makes the scheduler run.

This is a preemption request with cooperative handling. It is useful, but it has moved our question rather than answered it.

The signal handler itself is more interesting. It can run even while A is executing a tight loop. How did that happen?

The operating system arranges signal delivery to the target thread. The handler executes on that thread, with the interrupted execution state made available through a signal context. On return through the signal-return machinery, execution can continue from that saved state.

Another application thread is not running the handler on A's behalf. There may be another thread requesting an interruption, but the code handling it executes on the interrupted thread. In this experiment, the timer supplies the request, so we do not need a separate application thread even for that.

These are three different jobs: requesting an interruption, delivering it, and switching to another computation. Keeping them separate helped me understand what was happening.

Can we change what happens after the handler returns?

With a SA_SIGINFO handler, we can inspect the interrupted context. This excerpt reads the saved program counter using the offsets used by the macOS ARM64 experiment:

Rust
const UC_MCONTEXT_OFFSET: usize = 48;
const MC_PC_OFFSET: usize = 272;

// Inside the signal handler; these offsets are platform-specific.
let mctx = unsafe {
    *(ucontext.add(UC_MCONTEXT_OFFSET) as *const *const u8)
};
let interrupted_pc = unsafe {
    *(mctx.add(MC_PC_OFFSET) as *const u64)
};

The offsets came from inspecting the system structures with a small C helper. These are not constants to copy into a portable library and hope for the best.

First I wanted to establish that the captured PC really pointed into the work function. Then the next experiment changed it to point at a different function. That test ran in a forked child so that an invalid redirect would not take down the rest of the experiments. The destination wrote a message and exited with a distinctive exit code.

That establishes something quite specific: on this setup, modifying the saved PC can change where execution continues after the signal handler returns.

It does not yet establish that we can safely pause and resume arbitrary computation. Exiting at a new destination is much easier than returning to the old one with everything intact.

Why not redirect straight to yield_now()?

That was the next experiment.

The handler put the interrupted PC into the saved link register and changed the saved PC to yield_now. The intention was that yield_now would switch to the scheduler and, when resumed, return to the interrupted instruction.

Control did reach the scheduler. But the computation could become corrupted or crash.

The problem is that our interrupted loop never made a function call. It never agreed that the caller-saved registers could be overwritten. They may contain values needed by the very next instruction.

The calling convention that made our cooperative switch relatively small is not sufficient here.

So we add a trampoline before the ordinary Rust yield function. Here is an abbreviated version of the actual experimental trampoline; the omitted instructions save and restore the intervening integer register pairs:

Rust
#[unsafe(naked)]
unsafe extern "C" fn preempt_trampoline() {
    naked_asm!(
        "stp x0,  x1,  [sp, #-160]!",
        "stp x2,  x3,  [sp, #16]",
        // ... save x4 through x17 ...
        "stp x18, x30, [sp, #144]",

        "bl {yield_now}",

        "ldp x18, x30, [sp, #144]",
        // ... restore x4 through x17 ...
        "ldp x2,  x3,  [sp, #16]",
        "ldp x0,  x1,  [sp], #160",
        "ret",
        yield_now = sym yield_now,
    );
}

This is not a complete copy-paste implementation. More importantly, the complete version in the experiment is still not a correct general-purpose asynchronous preemption trampoline.

The mechanism is worth following anyway. The signal context initially contains the interrupted state. The handler arranges to enter the trampoline. The trampoline pushes additional register values onto A's stack, then calls yield_now. The cooperative switch saves its usual context and resumes the scheduler.

At this point, A's suspended state is spread across its stack and its context structure. It does not all have to live in one struct. When A is selected again, those layers unwind in the other direction: the context switch returns, the yield function returns, and the trampoline restores its saved values before branching back.

The counting example produced the expected final counts. That was encouraging. But the original notes called this "full register preservation," and that description goes too far.

The handler has already replaced the original LR with the interrupted PC. The trampoline therefore saves a return destination, not the original LR value that the interrupted computation may still need. It also does not preserve the condition flags or the full floating-point and SIMD state. An interruption between a comparison and its conditional branch is enough to make flags matter. A leaf function may still need its original LR to return.

There are platform stack conventions to respect too, including space below the interrupted stack pointer that code may be allowed to use. Pushing a new frame onto an arbitrary interrupted stack requires more care than pushing one at an ordinary call boundary.

So the experiment explains a route into the scheduler. It does not prove transparent resumption at every instruction. Those are different milestones.

Suppose we save everything. Are we done?

Not quite.

Imagine A is interrupted inside a library function while holding an internal lock. We run B, which enters the same library and waits for that lock. Depending on the locking mechanism, B might block the OS worker that A needs in order to resume and release it. Thread ownership assumptions can cause other problems as well.

Or consider interrupting our scheduler halfway through updating its own state. Correctly restoring the registers later does not make it safe to enter the scheduler again while its invariants are temporarily broken.

This is where "save the CPU state" stops being a sufficient description of preemption. We also need to know whether changing which computation runs is valid at that location.

Go has information that our experiment does not. On supported Unix platforms, its runtime can request asynchronous preemption with a targeted signal, commonly SIGURG. A monitoring path can decide that a running goroutine should be preempted; the signal handling path on the target OS thread checks whether it can safely arrange that transfer.

The runtime and compiler cooperate on identifying asynchronous safe points. The checks include runtime state, whether the interrupted instruction location is suitable, and whether there is enough stack space for the injected path. If the location is unsuitable, the handler can return without scheduling another goroutine. A request is not an obligation to switch immediately.

At a suitable location, an assembly entry path preserves the required state and enters the runtime. This is the more complete version of what we are trying to investigate with the trampoline.

Go also retains synchronous preemption mechanisms associated with compiler-generated checks. Asynchronous and cooperative mechanisms complement each other; they are not mutually exclusive descriptions of the runtime.

Blocking system calls are another case again. If an OS thread is waiting in the kernel, Go can arrange for other threads to carry on executing goroutines. That is not the same operation as rewriting the continuation of CPU-bound user code. Signals can also cause some system calls to return early with interruption errors, so "the syscall cannot be affected" would be too strong a claim.

Could the saved computation resume on another thread?

Once A is suspended, its stack is still in memory and its context is data. Nothing in the basic register-loading sequence requires the OS thread that resumes it to be the same one that saved it.

That suggests another experiment: put runnable green threads into a shared queue and let several OS workers take turns running them.

The implementation uses a Mutex<VecDeque<GreenThread>>. A worker removes a green thread, switches into it, and puts it back if it yields. Another worker can then remove it and resume it. These experiments use cooperative yields. They do not combine multi-worker migration with the earlier signal-based preemption mechanism.

The yield path needs to find the scheduler belonging to the worker it is currently running on. The implementation uses thread-local pointers:

Rust
thread_local! {
    static WORKER_PTR: Cell<*mut Worker> =
        const { Cell::new(std::ptr::null_mut()) };
    static CURRENT_GT: Cell<*mut GreenThread> =
        const { Cell::new(std::ptr::null_mut()) };
}

This exposes another assumption we were previously getting for free. A saved register value comes along with the green thread. The OS thread's thread-local storage does not.

If we cache a pointer to worker A, yield, and resume on worker B, the cached value still points to worker A. Faithfully preserving it is now part of the problem.

The experiment uses #[inline(never)] on the worker yield function as a mitigation against the compiler carrying worker-local information across yield boundaries in the surrounding code. It also uses raw pointers for the shared context accesses to avoid introducing conflicting mutable references. Neither choice is a general proof that arbitrary Rust functions can safely migrate between OS threads.

A function could hold thread-affine state, a borrowed reference into TLS, or a guard that must be released on its original thread. Rust's normal assumptions about a function executing on one thread do not disappear because our assembly can move its stack pointer elsewhere.

The shared-queue test runs 10,000 green threads with repeated yields and checks that they all complete. It exercises the mechanism under more load, but it does not test all of those semantic constraints. A completion counter cannot tell us that every possible live value would have survived migration correctly.

Coming back to the original question

So where does the code that stops the computation run?

The actual transfer into the scheduler happens on the executing OS thread. For a cooperative yield, the computation calls into it. For asynchronous preemption, an external request and the operating system's signal machinery can give that thread a path into runtime code even though the interrupted computation never called it itself.

Another thread may request the interruption. It does not need to directly copy registers out of a remote core and replace them. The target thread performs the relevant save and transfer when the interruption is delivered and the runtime determines it is safe to proceed.

And where does the computation go?

Mostly, it stays where it was. Its stack and other memory remain allocated. The register state needed for resumption is written into memory too. Another computation uses the CPU for a while. Later, restoring the saved state lets the original one continue.

The part I had underestimated was not the assembly required to exchange a few register values. It was how much the validity of that exchange depends on where we stopped, what the compiler believed could happen there, and which state belongs to the computation rather than the OS thread.

Building the Rust experiments made those questions much harder to leave hidden behind "the runtime takes care of it." It also left a fairly concrete set of next experiments: preserve and test the original LR, flags, and vector state; define where preemption is allowed; and make the restrictions on migration explicit before trying to combine it with asynchronous interruption.

That seems like a more useful place to arrive than claiming we have rebuilt Go. We have a clearer account of how control can move between computations, and a clearer understanding of what still has to be true for that movement to be safe.
