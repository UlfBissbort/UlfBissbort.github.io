Exploring Go's Scheduling in Rust

A long-running computation behaves quite differently inside a Go goroutine and a Rust async task. Go can pause the computation and run another goroutine before it finishes. A typical Rust async executor cannot: once a task enters a CPU-heavy function, that worker is occupied until the function returns or the task yields.

This matters in production. If computations occupy every executor worker, unrelated tasks can stop making progress. A request handler, a timeout, or the task that reports an unhealthy service may all be waiting to run. The operating system still schedules threads normally; it is the executor that cannot schedule its other tasks.

Go does not eliminate CPU contention or promise bounded scheduling latency. But it can regain control while ordinary Go code is still computing—even inside a loop with no function calls. How does it do that? Where does the code that pauses the computation execute, and what must it save?

I wanted to work through this from first principles, so I built a basic version using highly unsafe Rust and ARM64 assembly on macOS. This is a proof of concept, with known correctness problems, not a runtime to put underneath a service. The useful part is seeing where control goes and what happens to the machine state along the way.

The worker is occupied

Here is a small Tokio example. Use the macros, rt, and time features to run it:

Rust
use std::{hint::black_box, time::{Duration, Instant}};

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let start = Instant::now();
    let compute = tokio::spawn(async {
        let mut total = 0u64;
        for i in 0u64..1_000_000_000 {
            total = total.wrapping_add(black_box(i));
        }
        println!("computation finished: {total}");
    });

    tokio::time::sleep(Duration::from_millis(10)).await;
    println!("10ms timer resumed after {:?}", start.elapsed());
    compute.await.unwrap();
}

The timer cannot resume while the loop is running. async changes how a function can suspend; it does not make every instruction interruptible by the executor. Tokio's cooperative scheduling budget cannot interrupt arbitrary computation inside a poll. Even an .await need not yield if the awaited operation completes immediately.

Compare that with Go, limiting execution to one Go processor:

Go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    runtime.GOMAXPROCS(1)
    start := time.Now()
    done := make(chan struct{})
    go func() {
        var total uint64
        for i := uint64(0); i < 1_000_000_000; i++ {
            total += i
        }
        fmt.Println("computation finished:", total)
        close(done)
    }()

    time.Sleep(10 * time.Millisecond)
    fmt.Println("10ms timer resumed after", time.Since(start))
    <-done
}

On modern Go with asynchronous preemption enabled, the timer can resume before the computation finishes. In one run on this machine, using Tokio 1.49.0 in release mode and Go 1.25.7:

Configuration The 10ms timer resumed after
Tokio, one worker 365ms
Go, GOMAXPROCS=1 15ms
Go, additionally GODEBUG=asyncpreemptoff=1 317ms

These are observations, not a performance comparison or latency guarantee. Disabling asynchronous preemption makes the Go timer wait through the loop too; function calls after the loop still provide synchronous scheduling opportunities. The question is whether another task can run during the computation.

In Rust, the usual response is to keep long CPU-bound work off the async workers, often using a bounded compute pool. That is good advice, but it does not explain how Go manages the alternative.

Saving a computation

Suppose computation A is running and we want B to use the same OS thread. A's stack and heap data can stay in memory. What cannot stay put is its register state: B will use those registers too. We need to save A's values and restore them when A resumes.

This gives us a saved execution context, not a portable serialization. Its addresses still refer to memory in this process. Switching stacks does not mean copying the stack, and it does not require saving the CPU's caches.

First, let A explicitly call our switching function. This is easier than interrupting an arbitrary instruction because the compiler knows about the call. It already accounts for caller-saved registers being clobbered. Our switching function must preserve the callee-saved state, together with the stack pointer and return address:

Rust
#[repr(C)]
struct Context {
    x19: u64, x20: u64, x21: u64, x22: u64, x23: u64,
    x24: u64, x25: u64, x26: u64, x27: u64, x28: u64,
    x29: u64,   // frame pointer
    x30: u64,   // link register
    sp:  u64,   // stack pointer
    d8:  u64, d9:  u64, d10: u64, d11: u64,
    d12: u64, d13: u64, d14: u64, d15: u64,
}

#[repr(C)] fixes the field layout used by the assembly. The d8–d15 fields preserve the lower 64 bits of eight SIMD registers, as required by the AArch64 calling convention. Omitting them was one of the bugs in the exploration. An integer-heavy example does not imply that the compiler only uses integer registers.

Here is the complete cooperative switch. It takes pointers to the old and new contexts in x0 and x1:

Rust
use std::arch::naked_asm;

#[unsafe(naked)]
unsafe extern "C" fn switch_context(
    _old: *mut Context,
    _new: *const Context,
) {
    naked_asm!(
        "stp x19, x20, [x0, #0]",
        "stp x21, x22, [x0, #16]",
        "stp x23, x24, [x0, #32]",
        "stp x25, x26, [x0, #48]",
        "stp x27, x28, [x0, #64]",
        "stp x29, x30, [x0, #80]",
        "mov x2, sp",
        "str x2, [x0, #96]",
        "stp d8, d9, [x0, #104]",
        "stp d10, d11, [x0, #120]",
        "stp d12, d13, [x0, #136]",
        "stp d14, d15, [x0, #152]",

        "ldp x19, x20, [x1, #0]",
        "ldp x21, x22, [x1, #16]",
        "ldp x23, x24, [x1, #32]",
        "ldp x25, x26, [x1, #48]",
        "ldp x27, x28, [x1, #64]",
        "ldp x29, x30, [x1, #80]",
        "ldr x2, [x1, #96]",
        "mov sp, x2",
        "ldp d8, d9, [x1, #104]",
        "ldp d10, d11, [x1, #120]",
        "ldp d12, d13, [x1, #136]",
        "ldp d14, d15, [x1, #152]",
        "ret",
    );
}

stp and ldp store and load register pairs. A naked function supplies the instruction sequence without a compiler-generated prologue or epilogue, which would otherwise assume an ordinary stack frame.

The interesting instructions are mov sp, x2 and ret. The first installs B's stack pointer. The second branches to the address we loaded into x30. That address is B's saved continuation: usually the instruction after its earlier call to switch_context. From B's perspective, that call has returned.

No second OS thread performs this exchange. The current thread executes the assembly and continues on a different stack. The OS may independently move that thread between physical cores.

Starting and yielding

A function that has never run has no saved context, so we construct one. This setup is extracted from the experiment; Context::zeroed() initializes every field to zero:

Rust
let stack = vec![0u8; 64 * 1024];
let stack_top = (stack.as_ptr() as u64 + stack.len() as u64) & !0xF;

let mut ctx = Context::zeroed();
ctx.sp = stack_top;
ctx.x30 = thread_wrapper as u64;
ctx.x19 = f as u64;

The stack grows downward from a 16-byte-aligned address. We retain ownership of the allocation until the green thread finishes. The entry wrapper calls f through x19, then calls thread_done to mark the thread finished and switch away. It must not return past the top of this manufactured stack. There are no guard pages or stack growth here.

The scheduler runs on the original OS stack. It selects a ready green thread and switches into it. A yield marks the current thread ready and switches back to the scheduler, represented as thread 0. This is the relevant path from the prototype:

Rust
fn yield_now() {
    unsafe {
        let rt = &mut *RT;
        let current = rt.current;
        rt.threads[current].state = ThreadState::Ready;
        rt.current = 0;

        let cur_ctx = &mut rt.threads[current].ctx as *mut Context;
        let sched_ctx = &rt.threads[0].ctx as *const Context;
        switch_context(cur_ctx, sched_ctx);
        // The scheduler has selected us again.
    }
}

RT is the prototype's global runtime pointer. This is intentionally low-level code, not a safe Rust abstraction: the runtime's mutable-reference lifetimes and reentrant access also need auditing. The important part here is the direction of the switch. Yielding restores the scheduler's context; it does not call the scheduling loop on the green thread's stack.

We can now switch between computations. But if A never calls yield_now, we are back to the Tokio example.

Getting control back

A timer alone is not sufficient. One experiment had SIGALRM set an atomic flag and a check_preempt() function yield when it saw the flag. Remove those checks from the loop and nothing gets scheduled. That is still cooperative.

The useful property of the signal is that its handler can run while A is computing. We arm a periodic timer with setitimer(ITIMER_REAL, ...) and install a handler with sigaction and SA_SIGINFO. The OS arranges for the receiving thread to execute the handler, passing it the saved execution context. Signal-return machinery normally restores that context and resumes the interrupted code.

But the saved context is writable.

First I tested redirecting its PC to a landing function that exited a forked child with a distinctive code. That isolated the question of whether redirection worked from the harder question of resuming correctly. It did work on this setup.

The next step was to redirect into a trampoline that would call our yield function. Here is the experimental handler, with the preemption counter omitted and the platform offsets written inline:

Rust
extern "C" fn preempt_handler(
    _sig: i32,
    _info: *const u8,
    ucontext: *mut u8,
) {
    unsafe {
        if (*RT).current == 0 { return; } // skip the scheduler

        // macOS ARM64 offsets, obtained from the system headers.
        let mctx = *(ucontext.add(48) as *const *mut u8);
        let pc = mctx.add(272) as *mut u64;
        let lr = mctx.add(256) as *mut u64;

        *lr = *pc; // experimental return destination; destroys original LR
        *pc = preempt_trampoline as u64;
    }
}

After the handler returns, execution enters preempt_trampoline rather than the interrupted loop. The trampoline runs on the green thread's stack. We have inserted a path to the scheduler without adding a call to the computation itself.

The requester and the switching code need not be on the same thread. Go can have another thread request preemption of a specific worker. Our experiment uses a process-wide timer instead. In both cases, the signal handler executes on the receiving thread—not on a helper thread reaching into another core's registers. The process-wide timer is sufficient for this single-worker experiment, not for reliably targeting arbitrary workers.

An interruption is not a function call

Why not set PC = yield_now directly?

Because the interrupted code never agreed to a function call. It might still need every caller-saved register. An ordinary Rust function is free to overwrite those registers, which is exactly what happened in the naive experiment: control reached the scheduler, but the computation could become corrupted or crash.

The trampoline saves more state before calling Rust. This abbreviated assembly shows the layout; the omitted pairs cover x4–x17 in both directions:

Asm
preempt_trampoline:
    stp x0,  x1,  [sp, #-160]!
    stp x2,  x3,  [sp, #16]
    // ... save x4–x17 at offsets 32–128 ...
    stp x18, x30, [sp, #144]

    bl yield_now

    ldp x18, x30, [sp, #144]
    // ... restore x4–x17 ...
    ldp x2,  x3,  [sp, #16]
    ldp x0,  x1,  [sp], #160
    ret

yield_now uses the cooperative context switch we already built. A's suspended state is now split between the 168-byte context and the additional values on its stack. Resuming A returns through the switch, the yield function, and finally the trampoline:

Text
A's loop → signal handler → signal return → trampoline
    → yield_now → scheduler → B runs
    → ... scheduler selects A ...
    → yield_now returns → trampoline restores → A's loop

The counting example reached the expected totals with this trampoline. My original notes called that “full register preservation.” It isn't. Several concrete counterexamples remain:

Missing requirement How the prototype can fail
Preserve the original LR The handler overwrites it with the interrupted PC. A leaf function may still need the original LR to return.
Preserve flags and full FP/SIMD state Interrupt between cmp and b.eq: a changed condition flag can choose the wrong branch. The saved d8–d15 values are not the complete vector state.
Respect the interrupted stack's conventions The injected frame needs space and must not overwrite live data below SP, including the platform's red zone.
Prevent unsafe reentry Checking current == 0 does not protect every scheduler transition, trampoline instruction, or library critical section.

There is also a scheduling problem that saving registers cannot fix. Suppose A is interrupted inside a library while holding an internal lock. B enters the same library and blocks the OS worker waiting for it. A now needs that worker to resume and release the lock.

A successful count is evidence for that workload. It is not evidence that arbitrary Rust code can be preempted safely.

What Go adds

Go's implementation supplies the missing coordination between the compiler, signal handler, stack machinery, and scheduler. On supported Unix systems, it uses SIGURG to request asynchronous preemption of a particular OS thread. The runtime's monitoring thread can request it when a goroutine has occupied a processor too long; that request is not a guarantee of immediate suspension.

The relevant branch in Go 1.25.7's doSigPreempt is compact:

Go
if wantAsyncPreempt(gp) {
    if ok, newpc := isAsyncSafePoint(gp, ctxt.sigpc(), ctxt.sigsp(), ctxt.siglr()); ok {
        ctxt.pushCall(abi.FuncPCABI0(asyncPreempt), newpc)
    }
}

The operation resembles our experiment: modify the signal context to inject a call. The important difference is the predicate. isAsyncSafePoint checks runtime state, available stack space, and compiler metadata for the interrupted PC. It rejects unsuitable locations, including runtime code and instruction sequences marked unsafe. Some restartable sequences require an adjusted resumption PC rather than the exact interrupted address.

The ARM64 pushCall also answers one of our concrete failure cases. Before replacing LR, it saves the original value on the stack. These are the relevant lines, with frame-pointer bookkeeping omitted:

Go
sp := c.sp() - 16
c.set_sp(sp)
*(*uint64)(unsafe.Pointer(uintptr(sp))) = c.lr()

c.set_lr(uint64(resumePC))
c.set_pc(uint64(targetPC))

The assembly path entered at asyncPreempt preserves the state needed to resume and transfers into the runtime. Go also retains synchronous preemption checks; signals complement them rather than replacing all cooperation with the compiler.

This explains why adding a signal handler to a Rust executor would not give it Go's guarantees. Go controls the execution model of the code it schedules. Our prototype is trying to suspend code compiled under different assumptions.

Resuming on another worker

Once a green thread is suspended, could another OS thread load its context? The later experiments put ready green threads into a shared Mutex<VecDeque<GreenThread>>. A worker runs one until it yields, then puts it back. Another worker can resume it. These are cooperative migration experiments, separate from the signal-based preemption example.

The complication is OS-thread-local state. A saved pointer to worker A remains a pointer to worker A after the computation resumes on worker B. TLS references, thread-affine resources, and guards can make migration invalid even if every register is faithfully restored. The prototype's #[inline(never)] mitigation around worker yields is not a general solution to those constraints.

Migration is therefore a useful extension of the context-switch experiment, but it is not needed to answer the original question. We can preempt A and schedule B on the same worker.

Back to the blocked executor

A Rust async executor normally gets control when a poll returns. Go has another route: an external preemption request can cause the executing thread to enter runtime code at a suitable location, preserve its state, and schedule another goroutine before the computation finishes.

Most of the paused computation stays in memory where it was. The state in registers is saved alongside it. There is no helper copying an entire computation out of a CPU; the interrupted thread performs the transfer.

That is the part I wanted to understand. The Rust experiment makes the transfer visible. Its failures explain why the register switch alone is not enough—and why, when writing an ordinary Rust async service, keeping CPU-heavy work off the executor's workers remains our responsibility.
