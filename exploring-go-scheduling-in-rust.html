Exploring Go's Scheduling in Rust

A long-running computation behaves quite differently inside a Go goroutine and a Rust async task. Go can pause the computation and run another goroutine before it finishes. A typical Rust async executor cannot: once a task enters a CPU-heavy function, that worker is occupied until the function returns or the task yields.

This matters in production. If computations occupy every executor worker, unrelated tasks can stop making progress. A request handler, a timeout, or the task that reports an unhealthy service may all be waiting to run. The operating system still schedules threads normally; it is the executor that cannot schedule its other tasks.

Go can regain control even inside a loop with no function calls. How does it do that? Where does the code that pauses the computation execute, and what must it save?

Let's reproduce the mechanism using unsafe Rust and ARM64 assembly on macOS: save a running function's state, switch stacks, then use a signal to interrupt a computation that never yields. We'll compare the resulting code with Go's runtime.

The worker is occupied

Run a CPU-bound task alongside a timer on one Tokio worker. Enable Tokio's macros, rt, and time features:

Rust
use std::{hint::black_box, time::{Duration, Instant}};

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let start = Instant::now();
    let compute = tokio::spawn(async {
        let mut total = 0u64;
        for i in 0u64..1_000_000_000 {
            total = total.wrapping_add(black_box(i));
        }
        println!("computation finished: {total}");
    });

    tokio::time::sleep(Duration::from_millis(10)).await;
    println!("10ms timer resumed after {:?}", start.elapsed());
    compute.await.unwrap();
}

The timer cannot resume while the loop is running. async changes how a function can suspend; it does not make every instruction interruptible by the executor. Tokio's cooperative scheduling budget cannot interrupt arbitrary computation inside a poll. Even an .await need not yield if the awaited operation completes immediately.

Compare that with Go, limiting execution to one Go processor:

Go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    runtime.GOMAXPROCS(1)
    start := time.Now()
    done := make(chan struct{})
    go func() {
        var total uint64
        for i := uint64(0); i < 1_000_000_000; i++ {
            total += i
        }
        fmt.Println("computation finished:", total)
        close(done)
    }()

    time.Sleep(10 * time.Millisecond)
    fmt.Println("10ms timer resumed after", time.Since(start))
    <-done
}

On modern Go with asynchronous preemption enabled, the timer can resume before the computation finishes. In one run on this machine, using Tokio 1.49.0 in release mode and Go 1.25.7:

Configuration The 10ms timer resumed after
Tokio, one worker 365ms
Go, GOMAXPROCS=1 15ms
Go, additionally GODEBUG=asyncpreemptoff=1 317ms

Disable asynchronous preemption and the Go timer waits through the loop too. Function calls after the loop still provide synchronous scheduling opportunities. The elapsed times vary; the distinction is whether another task runs during the computation.

For Rust services, a bounded compute pool keeps this work off the async workers. To understand Go's alternative, start with the state we need to save.

Saving a computation

To run B on A's OS thread, leave A's stack and heap data in place and save its register state to memory. B can then use those registers. Restoring A's values resumes A with its existing stack. The saved addresses remain specific to this process.

Start with an explicit call to switch_context. At a call boundary, the compiler already accounts for caller-saved registers being clobbered. Save the callee-saved state, stack pointer, and return address:

Rust
#[repr(C)]
struct Context {
    x19: u64, x20: u64, x21: u64, x22: u64, x23: u64,
    x24: u64, x25: u64, x26: u64, x27: u64, x28: u64,
    x29: u64,   // frame pointer
    x30: u64,   // link register
    sp:  u64,   // stack pointer
    d8:  u64, d9:  u64, d10: u64, d11: u64,
    d12: u64, d13: u64, d14: u64, d15: u64,
}

#[repr(C)] fixes the field layout used by the assembly. The AArch64 calling convention requires preserving the lower 64 bits of d8–d15, even for integer-heavy workloads: the compiler can use those registers too.

Store the old context through x0 and load the new one through x1:

Rust
use std::arch::naked_asm;

#[unsafe(naked)]
unsafe extern "C" fn switch_context(
    _old: *mut Context,
    _new: *const Context,
) {
    naked_asm!(
        "stp x19, x20, [x0, #0]",
        "stp x21, x22, [x0, #16]",
        "stp x23, x24, [x0, #32]",
        "stp x25, x26, [x0, #48]",
        "stp x27, x28, [x0, #64]",
        "stp x29, x30, [x0, #80]",
        "mov x2, sp",
        "str x2, [x0, #96]",
        "stp d8, d9, [x0, #104]",
        "stp d10, d11, [x0, #120]",
        "stp d12, d13, [x0, #136]",
        "stp d14, d15, [x0, #152]",

        "ldp x19, x20, [x1, #0]",
        "ldp x21, x22, [x1, #16]",
        "ldp x23, x24, [x1, #32]",
        "ldp x25, x26, [x1, #48]",
        "ldp x27, x28, [x1, #64]",
        "ldp x29, x30, [x1, #80]",
        "ldr x2, [x1, #96]",
        "mov sp, x2",
        "ldp d8, d9, [x1, #104]",
        "ldp d10, d11, [x1, #120]",
        "ldp d12, d13, [x1, #136]",
        "ldp d14, d15, [x1, #152]",
        "ret",
    );
}

stp and ldp store and load register pairs. A naked function supplies the instruction sequence without a compiler-generated prologue or epilogue, which would otherwise assume an ordinary stack frame.

mov sp, x2 installs B's stack pointer. ret branches to B's saved x30: usually the instruction after its earlier call to switch_context. That call now returns on B's stack.

No second OS thread performs this exchange. The current thread executes the assembly and continues on a different stack. The OS may independently move that thread between physical cores.

Starting and yielding

For a function that has never run, construct its initial context. Allocate a stack and set the entry address; Context::zeroed() initializes every field to zero:

Rust
let stack = vec![0u8; 64 * 1024];
let stack_top = (stack.as_ptr() as u64 + stack.len() as u64) & !0xF;

let mut ctx = Context::zeroed();
ctx.sp = stack_top;
ctx.x30 = thread_wrapper as u64;
ctx.x19 = f as u64;

Keep the allocation alive until the green thread finishes. Its stack grows downward from the aligned address, with a fixed 64KB capacity and no guard page. thread_wrapper calls f through x19, then calls thread_done to mark it finished and switch away rather than return past the top of the stack.

The scheduler runs on the original OS stack as thread 0. It selects a ready green thread and switches into it. To yield, mark the running thread ready and restore thread 0's context:

Rust
fn yield_now() {
    unsafe {
        let rt = &mut *RT;
        let current = rt.current;
        rt.threads[current].state = ThreadState::Ready;
        rt.current = 0;

        let cur_ctx = &mut rt.threads[current].ctx as *mut Context;
        let sched_ctx = &rt.threads[0].ctx as *const Context;
        switch_context(cur_ctx, sched_ctx);
        // The scheduler has selected us again.
    }
}

RT is a global runtime pointer. Yielding restores the scheduler's context instead of calling its loop on the green thread's stack. The &mut Runtime access requires exclusive ownership across suspension; reentrant access through RT can violate that requirement.

A function that never calls yield_now still occupies the worker indefinitely.

Getting control back

Setting a flag from a timer handler does not solve this. A check_preempt() function could read that flag and yield, but the computation would still have to call it.

Instead, use the signal to redirect execution. Arm a periodic timer with setitimer(ITIMER_REAL, ...) and install a handler with sigaction and SA_SIGINFO. The OS runs the handler on the receiving thread and passes it the saved execution context. Signal return restores that context.

Change its PC to enter preempt_trampoline rather than resume the loop. Put the interrupted PC in LR as the return destination. This version overwrites the original LR; we'll address that below. The handler uses the macOS ARM64 offsets directly:

Rust
extern "C" fn preempt_handler(
    _sig: i32,
    _info: *const u8,
    ucontext: *mut u8,
) {
    unsafe {
        if (*RT).current == 0 { return; } // skip the scheduler

        // macOS ARM64 offsets, obtained from the system headers.
        let mctx = *(ucontext.add(48) as *const *mut u8);
        let pc = mctx.add(272) as *mut u64;
        let lr = mctx.add(256) as *mut u64;

        *lr = *pc; // experimental return destination; destroys original LR
        *pc = preempt_trampoline as u64;
    }
}

Signal return enters the trampoline on the green thread's stack. The computation contains no call to it.

The handler executes on the receiving thread. A different thread can request preemption, as Go's runtime does, but it does not modify another core's registers directly. This example uses a process-wide timer with one worker; targeting multiple workers requires thread-directed signals.

Go makes that distinction explicit. Its preemptM requests preemption through signalM. On macOS, signalM is just:

Go
func signalM(mp *m, sig int) {
    pthread_kill(pthread(mp.procid), uint32(sig))
}

m represents an OS thread. Despite its name, pthread_kill sends a signal; SIGURG requests preemption rather than terminating the thread. The target thread handles that request. All Go runtime listings below are also copied verbatim from the Go 1.25.7 source.

An interruption is not a function call

Setting PC = yield_now directly lets an ordinary Rust function overwrite live caller-saved registers. At an arbitrary instruction, the interrupted code may need all of them.

Save x0–x18 and the injected return destination before calling Rust, then restore them after resumption. The omitted pairs below cover x4–x17 in both directions:

Asm
preempt_trampoline:
    stp x0,  x1,  [sp, #-160]!
    stp x2,  x3,  [sp, #16]
    // ... save x4–x17 at offsets 32–128 ...
    stp x18, x30, [sp, #144]

    bl yield_now

    ldp x18, x30, [sp, #144]
    // ... restore x4–x17 ...
    ldp x2,  x3,  [sp, #16]
    ldp x0,  x1,  [sp], #160
    ret

yield_now saves the cooperative context and restores the scheduler. A's state is split between the 168-byte context and its stack. Resumption returns through the switch, yield function, and trampoline:

Text
A's loop → signal handler → signal return → trampoline
    → yield_now → scheduler → B runs
    → ... scheduler selects A ...
    → yield_now returns → trampoline restores → A's loop

This trampoline still loses machine state and permits unsafe reentry:

Missing requirement How the prototype can fail
Preserve the original LR The handler overwrites it with the interrupted PC. A leaf function may still need the original LR to return.
Preserve flags and full FP/SIMD state Interrupt between cmp and b.eq: a changed condition flag can choose the wrong branch. The saved d8–d15 values are not the complete vector state.
Respect the interrupted stack's conventions The injected frame needs space and must not overwrite live data below SP, including the platform's red zone.
Prevent unsafe reentry Checking current == 0 does not protect every scheduler transition, trampoline instruction, or library critical section.

Locks impose another constraint. If A is interrupted while holding an internal library lock and B blocks the OS worker waiting for it, A cannot resume to release it. Register preservation alone cannot prevent this deadlock.

What Go adds

After SIGURG reaches the worker, doSigPreempt decides whether to inject a call:

Go
func doSigPreempt(gp *g, ctxt *sigctxt) {
    // Check if this G wants to be preempted and is safe to
    // preempt.
    if wantAsyncPreempt(gp) {
        if ok, newpc := isAsyncSafePoint(gp, ctxt.sigpc(), ctxt.sigsp(), ctxt.siglr()); ok {
            // Adjust the PC and inject a call to asyncPreempt.
            ctxt.pushCall(abi.FuncPCABI0(asyncPreempt), newpc)
        }
    }

    // Acknowledge the preemption.
    gp.m.preemptGen.Add(1)
    gp.m.signalPending.Store(0)

    if GOOS == "darwin" || GOOS == "ios" {
        pendingPreemptSignals.Add(-1)
    }
}

gp is the goroutine; ctxt wraps the interrupted machine state. isAsyncSafePoint checks runtime state, stack space, and compiler metadata for the interrupted PC. It rejects runtime code and instruction sequences marked unsafe. For restartable sequences, it can adjust the resumption PC. If the checks fail, no call is injected, but the request is still acknowledged and signalPending is cleared. Receiving a signal and switching goroutines are separate decisions.

On ARM64, pushCall saves the original LR before replacing it—the step missing from our handler:

Go
func (c *sigctxt) pushCall(targetPC, resumePC uintptr) {
    // Push the LR to stack, as we'll clobber it in order to
    // push the call. The function being pushed is responsible
    // for restoring the LR and setting the SP back.
    // This extra space is known to gentraceback.
    sp := c.sp() - 16 // SP needs 16-byte alignment
    c.set_sp(sp)
    *(*uint64)(unsafe.Pointer(uintptr(sp))) = c.lr()
    // Make sure a valid frame pointer is saved on the stack so that the
    // frame pointer checks in adjustframe are happy, if they're enabled.
    // This is not actually used for unwinding.
    *(*uint64)(unsafe.Pointer(uintptr(sp - goarch.PtrSize))) = c.r29()
    // Set up PC and LR to pretend the function being signaled
    // calls targetPC at resumePC.
    c.set_lr(uint64(resumePC))
    c.set_pc(uint64(targetPC))
}

There are two continuation addresses to preserve: the interrupted PC, where this computation resumes, and the original LR, which the interrupted function may need when it returns. Our handler overwrote the latter. Go puts it on the stack, keeps SP aligned, and records frame-pointer state for the runtime's stack checks.

The injected target is asyncPreempt. Its ARM64 assembly saves NZCV and FPSR at lines 27–30, then restores them at lines 64–67. Those are the condition flags and floating-point status missing from our trampoline. Its register-save set follows Go's own ABI; it is not a drop-in implementation for arbitrary Rust code. Go also retains synchronous preemption checks.

Go's compiler supplies the safe-point metadata its runtime needs. A signal handler added to a Rust executor has no equivalent information about arbitrary Rust code.

Resuming on another worker

To move a suspended green thread between workers, put ready threads in a shared Mutex<VecDeque<GreenThread>>. A worker runs one until it yields, then puts it back. Another worker can load its context. This extension uses cooperative yields, separate from signal-based preemption.

OS-thread-local state does not move with the stack. A cached pointer to worker A still points to A after resumption on B. Migration must exclude live thread-affine resources and guards, and worker-local pointers must be reacquired on the new worker. Preserving their old register values is precisely the wrong behavior.

Preemption does not require migration: A and B can take turns on the same worker.

Back to the blocked executor

A Rust async executor normally gets control when a poll returns. Go has another route: an external preemption request can cause the executing thread to enter runtime code at a suitable location, preserve its state, and schedule another goroutine before the computation finishes.

The interrupted thread performs the transfer. Its stack stays allocated; its live register state is saved to memory. Go coordinates that operation with compiler-defined safe points. In an ordinary Rust async service, long-running computations still need explicit scheduling boundaries or a separate compute pool.

I like playing with code like this. Pushing the limits, seeing what works, then find where it breaks. Clearly this code is nowhere close to sufficiently well tested for production use. But maybe this mechanism may turn out to be useful in Zef some day.
