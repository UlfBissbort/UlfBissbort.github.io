Guide to Updating Your Mac After the CA Incident

You can copy this entire guide into a coding agent such as Codex, Claude Code, or pi and ask it to perform the updates on your Mac. Have it inspect your installations first, apply the relevant steps, and report what it verified and anything that still needs your attention.

A TLS client accepts a website certificate when it can build a valid chain back to a certificate authority it trusts. The eMudhra incident exposed trivially weak private keys in intermediate CAs. An attacker with those keys could issue certificates that clients would accept through the affected chains.

The fix is to remove those trust paths. On a Mac, that means visiting several places: macOS Keychain, shared certificate bundles, Python environments, and runtimes that embed their own roots.

I went through this on my Mac on 23 October 2026. Python had old pip installations scattered across project environments. Node still bundled roots removed from the updated CA bundle. Bun needed its own update. Here is the procedure, including the checks and the places where an apparently successful update can leave an older copy active.

The shell commands below use Bash syntax. Run them in bash, or have your agent translate them to your shell. If you give this article to an agent, ask it to inventory first, update only installed tools, preserve project dependencies, and finish with a report of verified changes and unresolved installations.

Find the installations you actually use

Start with executable paths and versions:

Bash
for tool in python3 pip pip3 uv node bun brew; do
  command -v "$tool" || true
done
python3 --version
python3 -m pip --version
uv --version
node --version
bun --version

Skip tools that are absent. Check version-manager installations and project-specific runtimes too. An executable under ~/.bun/bin, for example, has a different update path from one managed by Homebrew.

Find virtual environments under your project directories:

Bash
find "$HOME/dev" -type f -name pyvenv.cfg -print

Replace ~/dev with your actual project roots. Each result identifies an environment whose packages need checking. On this machine, that search found 23 environments; 18 had pip installed.

Update the shared CA bundle

For an existing Homebrew installation:

Bash
brew update
HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK=1 \
  brew upgrade ca-certificates

brew list --versions ca-certificates
CA_FILE="$(brew --prefix)/etc/ca-certificates/cert.pem"
test -s "$CA_FILE" && printf '%s\n' "$CA_FILE"

If brew list --versions certifi or brew list --versions uv shows an installed package, upgrade it the same way:

Bash
HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK=1 brew upgrade certifi
HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK=1 brew upgrade uv

The versions installed here were ca-certificates 2026-10-20, certifi 2026.10.19, and uv 0.13.5. Use current releases meeting the advisory's minimums: certifi 2026.10.19 and uv 0.13.4.

Homebrew's dependent-upgrade behavior matters. My initial command started upgrading unrelated software, including a new Python major version, and encountered linking conflicts. Keep the dependent check disabled for these targeted upgrades. Resolve any Homebrew errors before counting a package as updated.

Distrust G3 in macOS Keychain

The updated bundle retains emSign Root CA – G1. It excludes emSign ECC Root CA – G3, emSign Root CA – C1, and emSign ECC Root CA – C3. Preserve the unaffected G1 root.

On this Mac, Apple's system roots contained G1 and G3. Inspect yours:

Bash
security find-certificate -a -c emSign -Z \
  /System/Library/Keychains/SystemRootCertificates.keychain

For G3, match this SHA-256 fingerprint before changing trust:

Text
86A1ECBA089C4A8D3BBE2734C612BA341D813E043CF9E8A862CD5C57A36BBE6B

The following block exports G3, checks its fingerprint, and records an SSL denial for the current user:

Bash
(
  set -eu
  work=$(mktemp -d)
  trap 'rm -rf "$work"' EXIT
  security find-certificate -c 'emSign ECC Root CA - G3' -p \
    /System/Library/Keychains/SystemRootCertificates.keychain \
    > "$work/g3.pem"

  fingerprint=$(openssl x509 -in "$work/g3.pem" -noout \
    -fingerprint -sha256 | cut -d= -f2 | tr -d ':')
  test "$fingerprint" = \
    '86A1ECBA089C4A8D3BBE2734C612BA341D813E043CF9E8A862CD5C57A36BBE6B'

  security add-trusted-cert -r deny -p ssl \
    -k "$HOME/Library/Keychains/login.keychain-db" "$work/g3.pem"
  security verify-cert -c "$work/g3.pem" -p ssl
)

The final verification should fail with kSecTrustResultDeny. Inspect the stored rule with security dump-trust-settings. If the certificate is absent, inspect the other installed roots rather than importing an arbitrary replacement.

This rule applies to SSL validation through macOS trust services for your account. Administrator-level trust settings, other user accounts, and applications with independent certificate stores require their own checks.

Update pip in each Python environment

pip carries a vendored CA bundle. Install pip 26.2.2 or later wherever pip is used. Updating standalone certifi leaves an older pip's embedded bundle in place.

For each virtual environment, select its interpreter explicitly:

Bash
PY="/absolute/path/to/project/.venv/bin/python"
"$PY" --version
"$PY" -m pip --version

Python 3.10 or later can install pip 26.2.2. For a compatible environment that already contains pip, bootstrap using the wheel and hash supplied in the advisory:

Bash
"$PY" -m pip install --no-deps \
  'pip @ https://files.pythonhosted.org/packages/3f/06/3e4420302363fbb71be3c7f35ce042f54bfca330e3e66b3a2e3c4cca579f/pip-26.2.2-py3-none-any.whl#sha256=fd7f4dfa8190e014013b9f08f3e973f4e4c26ffd179a204895533a7254813a70'

"$PY" -m pip --version

I checked that URL and digest against the PyPI metadata for pip 26.2.2, then downloaded the wheel and independently checked its SHA-256 before installation.

Update certifi and uv where they are already installed:

Bash
if "$PY" -m pip show certifi >/dev/null 2>&1; then
  "$PY" -m pip install --upgrade 'certifi>=2026.10.19'
fi
if "$PY" -m pip show uv >/dev/null 2>&1; then
  "$PY" -m pip install --upgrade 'uv>=0.13.4'
fi
"$PY" -m pip check

Repeat for the other environments. Keep environments without pip as they are. Review any dependency conflicts reported by pip check and update project constraints separately where necessary.

Base interpreters and older Python

For a python.org installation, use the interpreter under /Library/Frameworks/Python.framework/Versions/<version>/bin/ and apply the same compatible pip and certifi updates. Check free-threaded installations separately.

For Homebrew- or uv-managed Python, use its manager to update the interpreter, then inspect its pip version again. Preserve the Python minor version used by existing projects. Also check the bundled bootstrap pip with:

Bash
"$PY" -I -m pip --version
"$PY" -m ensurepip --version

A user-site pip installation can make ordinary python -m pip report the fixed version while isolated mode still loads an older managed copy. We encountered exactly this distinction. Treat such an installation as partially mitigated until its managed and bootstrap copies are updated. Avoid blanket --break-system-packages overrides across managed interpreters.

Python 3.9 cannot run pip 26.2.2. Recreate those project environments on a supported Python release and reinstall their dependencies. Stop using the older pip for network operations in the meantime. Apple's Command Line Tools Python is managed through Apple's software updates.

On this Mac, 17 project environments accepted the fixed pip. One Python 3.9 environment remained unresolved, and an older Poetry environment referenced a removed interpreter. Record these exceptions explicitly.

Make Node use the updated bundle

The installed Node 25.9.0 exposed all four emSign roots in its bundled list. Adding --use-system-ca retained those roots and added system certificates. NODE_EXTRA_CA_CERTS also adds certificates.

To select the updated Homebrew bundle instead, apply these settings in the shell that will launch Node:

Bash
export SSL_CERT_FILE="$(brew --prefix)/etc/ca-certificates/cert.pem"
export NODE_OPTIONS="${NODE_OPTIONS:+$NODE_OPTIONS }--use-openssl-ca"

Inspect existing NODE_OPTIONS and NODE_EXTRA_CA_CERTS first. Remove conflicting CA-selection options and review any additional bundle that could restore removed trust. Preserve unrelated runtime options.

Check the inherited configuration and ordinary HTTPS:

Bash
node -p 'JSON.stringify({options:process.env.NODE_OPTIONS, ca:process.env.SSL_CERT_FILE})'
node -e 'require("https").get("https://pypi.org/", r => {
  console.log(r.statusCode, r.socket.authorized); r.resume();
}).on("error", e => { console.error(e); process.exitCode = 1; })'

Persist these variables in the shell configuration you actually use. For zsh, that can be ~/.zshenv. For Nushell, find the active file with nu -c 'print $nu.env-path', then set $env.SSL_CERT_FILE and $env.NODE_OPTIONS there. Use the resolved absolute bundle path.

For future applications launched through your current macOS login session, launchctl setenv can set the same variables. Apply them again at login through a LaunchAgent if needed. Services with explicit environments need their configuration updated separately.

Prefer a maintained Node release whose default trust has been verified as fixed when one is available. Explicit application ca options and additional certificate bundles remain separate inputs to review.

Update Bun itself

Bun 1.2.18 still exposed G3, C1, and C3. Setting SSL_CERT_FILE to an empty file and supplying Node's CA option left Bun's fetch requests working. The Node configuration above therefore provided no useful assurance for that Bun installation.

Bun 1.4.4, the release tested here, exposed only G1 among the emSign roots. For a standalone installation, use bun upgrade; for a Homebrew installation, update its installed formula through Homebrew. Verify the selected executable afterward:

Bash
command -v bun
bun --version
bunx --version

On this Mac, I downloaded the ARM64 release archive directly from Bun's GitHub release, verified its digest against the release API, and replaced ~/.bun/bin/bun. The existing bunx symlink picked up the same binary.

Inspect the exposed bundled roots:

Bash
bun -e '
const { rootCertificates } = require("tls");
const { X509Certificate } = require("crypto");
console.log(rootCertificates
  .map(pem => new X509Certificate(pem).subject)
  .filter(subject => /emSign/i.test(subject)));
'

On 1.4.4, the output contained emSign Root CA – G1 only. Then exercise both the runtime and the package manager:

Bash
bun -e 'fetch("https://pypi.org/").then(r => {
  console.log(r.status); if (!r.ok) process.exitCode = 1;
}).catch(e => { console.error(e); process.exitCode = 1; })'

(
  set -eu
  work=$(mktemp -d)
  trap 'rm -rf "$work"' EXIT
  cd "$work"
  printf '%s\n' \
    '{"private":true,"dependencies":{"is-number":"7.0.0"}}' \
    > package.json
  bun install --ignore-scripts --no-cache
  test -f node_modules/is-number/index.js
)

Both checks passed after the update. Review custom ca settings, .npmrc, and bunfig.toml if your applications or package installations supply their own trust configuration.

Restart and account for what remains

Restart terminals, IDEs, development servers, and long-running Python, Node, and Bun processes. Existing processes retain their executable and environment. Log out and back in when applying login-time settings, then verify the effective environment again.

Finish with a short report:

Component Evidence to record
Homebrew certificates Installed bundle version and resolved path
macOS trust G3 fingerprint and explicit SSL deny result
Python Interpreter path, pip version, certifi version, isolated-mode and bootstrap checks
Node Executable version, effective CA options, successful HTTPS
Bun Executable version, exposed roots, runtime and installer checks
Exceptions Older Python, broken environments, custom bundles, services awaiting restart

A successful HTTPS request establishes connectivity. Inspecting the certificate list establishes which roots that interface exposes. An explicit denial test establishes rejection through the tested validation path. Keep those results distinct in the report.

Containers and remote machines have their own installations and certificate bundles. Rebuild container images with fresh base images and disabled build caching, then repeat the relevant checks inside them. Browsers, Electron applications, Java runtimes, and other software with separate trust stores also need their own updates.

The useful unit of work is each TLS client's effective trust configuration. Follow the executable, its environment, and the certificates it actually loads; then verify the result after restarting it.
