Get that async off my Porch!


Gopher in Python's async hell: mental reenactment by the author.

Today's common wisdom is: "Python is not that great at async programming" and how Go is so much better at it. This seems to be part of common programmer wisdom, at least those who have suffered through enough race conditions, GIL issues, deadlocks, performance problems.

I used to think this. This post will be like swearing in the church of the gopher: I will claim that as a language, Python allows for better concurrent and parallel programming than Go does. Hear me out.

Go has a lot going for it in the async world. I think it boils down to 3 things that make it great out of the box

  • I never have to think about function coloring (i.e. is this a regular function or a coroutine)
  • errors as values (vs. exceptions)
  • automatic and reasonable scheduling defaults with a runtime under the hood that mostly "just works"

I strongly agree with all of these points. But Go's sweet spot is building regular backend services for CRUD apps or microservices. Two things I'm not particularly excited about these days. You very quickly grow beyond Go's sweet spot if you try to build reliable and predictable systems for core infrastructure. Or if you you prefer building flexible libraries rather than microservices in factoring out commonality and complexity.

I am very much in the first camp these days.

"But surely you won't try to tell me that Python's asyncio is better," you may be thinking. No, I won't. Asyncio's original—and still widely used—create_task() and gather() APIs do not enforce structured concurrency. Trio's nurseries make task ownership, cancellation, and error propagation structural. Python 3.11's TaskGroup has since brought similar guarantees to asyncio, but much of the ecosystem and its established programming style grew around the older model.

So what gives? How can Python out-gopher go?
I am not saying that standard Python is better than Go in its regular form But I am saying that on a fundamental language level, Python does allow for a better system under the hood. One that is safer for critical systems, more flexible and in some cases even more performant.

Well, relying on what is in my opinion Python's greatest power: it is a Lisp in snake's clothing. As a language, one can use it as a thin syntactic veneer to wrap around whichever library one is building.

Let's lean in and see what we can do.

  1. get rid of function coloring. If I never have to write an async in my application level code, I will be a happier man
  2. allow composition of computation built around a data flow paradigm
  3. embrace distributed systems at the language level: don't throw in the towel at the OS process and network boundary
  4. do not use exceptions as control flow constructs - prefer errors as values
